
TREE_DEPTH = 3

maximum leaves = 2^3 = 8

Leaves:
0 1 2 3 4 5 6 7

filledSubtrees[level] :
        the latest completed LEFT node at that level
        waiting for a RIGHT sibling


Initial Zero Setup

Z0 = 0
Z1 = hash(Z0, Z0)
Z2 = hash(Z1, Z1)

Initial Tree:

                ROOT = Z3
               /         \
             Z2           Z2
           /    \       /    \
         Z1      Z1   Z1      Z1
        /  \    / \   / \    / \
       Z0 Z0  Z0 Z0 Z0 Z0  Z0   Z0

filledSubtrees[0] = Z0
filledSubtrees[1] = Z1
filledSubtrees[2] = Z2


EXAMPLE:

1. INSERT A

    A inserted at index 0

    Binary index: 000

    LEVEL 0

        Index bit:
            0 → EVEN

        Meaning:
            A becomes LEFT child

        So:
            filledSubtrees[0] = A

        because:
            we are waiting for RIGHT sibling later

        Then compute parent:
            H1 = hash(A, Z0)

        Why Z0?
            Because right sibling doesn’t exist yet.


    LEVEL 1

        Shift index:
            000 >> 1 = 00

        Still EVEN.
        Meaning:
            H1 becomes LEFT subtree

        Store:
            filledSubtrees[1] = H1

        Then:
            H2 = hash(H1, Z1)

    LEVEL 2
        Again EVEN.

        Store:
            filledSubtrees[2] = H2

        Then:
            ROOT = hash(H2, Z2)

        After A Inserted:
            filledSubtrees
            level 0 → A
            level 1 → H1
            level 2 → H2

    Meaning:
        all LEFT branches waiting for right siblings.

2. INSERT B

    Now:
        B inserted at index 1

    Binary:
        001
    
    LEVEL 0
        LSB:
        1 → ODD

        Meaning:
            RIGHT child arrived

        So LEFT sibling already exists:
            filledSubtrees[0] = A

        Now compute:
            HAB = hash(A, B)

    LEVEL 1
        Shift:
            001 >> 1 = 000

        Now EVEN.

        Meaning:
            HAB becomes LEFT subtree

        Store:
            filledSubtrees[1] = HAB

        Then:
            HABZ = hash(HAB, Z1)
    
    LEVEL 2
        Again EVEN.
        Store:
            filledSubtrees[2] = HABZ
        Then:
            ROOT = hash(HABZ, Z2)

3. INSERT C

    Index:
        2 = 010
    
    LEVEL 0
        LSB: 0
        Even.
        Store:
            filledSubtrees[0] = C
        Then:
            HC = hash(C, Z0)

    LEVEL 1
        Shift:
            010 >> 1 = 001
        ODD now.

        Meaning:
            LEFT subtree already exists

        Which LEFT subtree?
            filledSubtrees[1] = HAB
        So:
            HABC = hash(HAB, HC)

    LEVEL 2
        Shift:
            001 >> 1 = 000
        EVEN.
        Store:
            filledSubtrees[2] = HABC
        Then:
            ROOT = hash(HABC, Z2)

IMPORTANT OBSERVATION

    After inserting C:

        filledSubtrees[0] = C
        filledSubtrees[1] = HAB
        filledSubtrees[2] = HABC

    Meaning:
        Level 0
            C waiting for D
        Level 1
            AB subtree waiting for CD subtree
        Level 2
            ABC subtree waiting for right half of tree

4. INSERT D
    Index:
        3 = 011

        LEVEL 0
        ODD.
        Use:
            filledSubtrees[0] = C
        Compute:
            HCD = hash(C, D)

        LEVEL 1
            Shift:
                011 >> 1 = 001
            ODD again.

            Use:
                filledSubtrees[1] = HAB

            Compute:
                HABCD = hash(HAB, HCD)


        LEVEL 2
            Shift:
                001 >> 1 = 000
                EVEN.

            Store:
                filledSubtrees[2] = HABCD

            Then:
                ROOT = hash(HABCD, Z2)


At every level:

EVEN index
    new LEFT subtree created
    → store it
ODD index
    RIGHT sibling arrived
    → combine with stored LEFT subtree


================================================================
v1-mainnet: INSERTING 4 LEAVES AT A TIME
================================================================

Everything above still holds. What changed is how many leaves go in per
operation (contracts/libraries/poolLib.sol insertChunk).

Every pool operation inserts exactly ONE chunk of 4 leaves:

    deposit     [ cm,     0,      0,   0 ]
    withdraw    [ change, fee,    0,   0 ]
    transfer    [ recv,   change, fee, 0 ]

nextIndex therefore always moves by 4, so every chunk starts at an index
that is a multiple of 4.

Why: hashing up the tree is the expensive part (~31k gas per Poseidon call
on-chain). One leaf at a time costs 20 hashes per note — 60 for a transfer.
A chunk costs:

    3 hashes   to combine the 4 leaves into one node:

                   N = hash( hash(l0, l1), hash(l2, l3) )

    18 hashes  to climb from level 2 to the root, exactly like the single-leaf
               walk above, but starting at level 2 with index = start >> 2

    = 21 hashes for the whole operation.

When the right pair is all zeros, hash(0, 0) is Z1 (a constant), so that hash
is skipped.

Zero leaves are ordinary leaves. An off-chain tree that inserts the same
4 leaves one by one ends at the same root, which is how the wallet's copy of
the tree (helpers/merkle.js) matches the contract. A zero leaf can never be
spent: spending needs a note whose commitment hashes to it.


Zero values (Z0 ... Z20)

    Hard-coded in poolLib.sol zeros(level) instead of stored per tree.
    Generated by scripts/gen_zeros.js:

        Z0 = 0
        Zi = Poseidon(Zi-1, Zi-1)

    Z20 is the root of an empty tree.


ROOT HISTORY

    A proof is built against the root the wallet sees. By the time the
    transaction lands, other operations may have moved the tree.

    The tree remembers its last 100 roots (ROOT_HISTORY_SIZE, was 10):

        rootHistory[100]          circular buffer
        knownRoot[root] = true    O(1) lookup

    Each insert writes the new root into the next slot and forgets the root
    it overwrites. A root stays valid for 99 more inserts and is evicted by
    the 100th (tested in test/noidpool-test.js "tree").
