================================================================================
        MENOID TESTNET DEPLOYMENTS — user-commitment (register) architecture
================================================================================
Last updated: 2026-07-15 — deposit circuit range-check fix rolled out to all 6
chains. See "DEPOSIT RANGE-CHECK FIX" at the bottom for what changed and why.

Architecture (all chains):
  - Users keep their REAL wallet address. The wallet signs the message
    "menoid_Wallet"; from that signature a BabyJubJub spending keypair and an
    encryption keypair are derived.
  - user_commitment = Poseidon(address mod p, spendPk.x, spendPk.y)
  - One-time on-chain registration: register(user_commitment). Re-register fails.
  - Note commitment = Poseidon(1, amount, r, user_commitment)
  - Nullifier       = Poseidon(2, commitment, r, spend_sk)
  - Deposit public signals: [amount, c1, c2, c2_enabled, relayerCommitment]
    (C2 = relayer fee note, optional / may be zero)
  - relayerCommitment = the relayer's own user commitment.
  - All amounts are range-constrained to 128 bits in EVERY circuit
    (deposit, transfer, withdraw).

                          DEPOSIT RANGE-CHECK FIX (2026-07-15)
================================================================================
WHAT WAS WRONG
  circuits/deposit_proof.circom never bounded its private amount inputs a1/a2
  (identical file on all 4 chain codebases). Its only value constraint is

      depositAmount === a1 + fee        // fee = c2_enabled * a2

  which is a FIELD equation mod the BN254 prime p. With no range check it is
  satisfiable by wrapping around p:

      msg.value = 1 wei
      a1 = 2^128 - 1
      a2 = (1 - a1) mod p
      => a1 + fee == 1 (mod p)  — proof verifies

  uc1 is private and unconstrained, so the attacker locks the inflated note to
  their own user commitment. 2^128-1 PASSES the RangeCheck(128) that
  transfer/withdraw already applied to a_ins, so the note stayed spendable and
  the pool could be drained. Transfer/withdraw were never affected.

THE FIX
  deposit_proof.circom now includes ./range_check.circom and constrains both
  amounts to 128 bits, matching transfer/withdraw:

      component a1Range = RangeCheck(128); a1Range.in <== a1;
      component a2Range = RangeCheck(128); a2Range.in <== a2;

  With both < 2^128, a1 + fee < 2^129 << p, so the equation holds over the
  integers and wraparound is impossible. depositAmount needs no separate bound
  since it is forced to equal a sum of two bounded values.
  Circuit: 859 non-linear constraints (was ~603). Public signals unchanged (5).

ROLLOUT
  New trusted setup for the deposit circuit on every chain => new deposit zkey
  + new deposit VK. Transfer/withdraw/new_root setups were NOT touched.
    - EVM x3 : fresh full deployment (NoidPool stores `immutable
               depositVerifier`, so the verifier cannot be swapped in place).
               Old pools remain live on the OLD vulnerable verifier — do not
               point anything at them.
    - Solana : program upgraded in place (VK is compiled in), same Program ID.
    - Aptos  : verifier::reinitialize_vks, same addresses.
    - Sui    : verifier::reinitialize_vks, same addresses.

VERIFIED
    - EVM       : 11/11 localnet E2E, incl. a new regression test asserting the
                  field-wrapping proof fails to witness ("Should reject a
                  deposit proof that wraps the field to mint value").
    - Solana    : 12/12 E2E green on the rebuilt program.
    - Aptos     : real testnet deposit accepted

STATE RECONCILIATION (2026-07-15)
  The backend treats its Mongo DB as the source of truth — no indexer scans the
  chain (see poolIndexer.js / aptosIndexer.js / suiIndexer.js). So the DB must
  hold exactly the leaves the chain holds, or every Merkle proof it builds is
  against a root that does not exist on-chain. State is keyed by NETWORK NAME,
  not pool address.

  Done after the migration:
    - monad / sepolia / base_sepolia : stale old-pool documents deleted
                                       (wallet/backend/reset_network_state.js)
    - aptos                          : pending queue drained + leaf recorded
                                       (wallet/backend/drain_aptos_pending.js)
    - sui                            : DB rebuilt from on-chain NoteCreatedEvent
                                       (wallet/backend/reconcile_sui_state.js)
    - solana                         : already consistent (both empty)

  Verified: DB leaf count == chain leaf count on all 6 networks, and the Aptos
  DB root matches pool::current_root exactly.
