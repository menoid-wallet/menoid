================================================================================
        MENOID TESTNET DEPLOYMENTS — user-commitment (register) architecture
================================================================================
Last updated: 2026-09-25 — ON-CHAIN ENCRYPTION KEY rollout. Every chain was
redeployed from scratch; all six pools start EMPTY. See "ON-CHAIN ENCRYPTION
KEY" at the bottom for what changed and why.

Architecture (all chains):
  - Users keep their REAL wallet address. The wallet signs the message
    "menoid_Wallet"; from that signature a BabyJubJub spending keypair and an
    encryption keypair are derived.
  - user_commitment = Poseidon(address mod p, spendPk.x, spendPk.y)
  - One-time on-chain registration:
        register(user_commitment, encryption_public_key)
    Re-register fails. BOTH values live on-chain, so a sender can resolve a
    receiver from the chain alone — no backend, no database.
  - Note commitment = Poseidon(1, amount, r, user_commitment)
  - Nullifier       = Poseidon(2, commitment, r, spend_sk)
  - Deposit public signals: [amount, c1, c2, c2_enabled, relayerCommitment]
    (C2 = relayer fee note, optional / may be zero)
  - relayerCommitment = the relayer's own user commitment.
  - All amounts are range-constrained to 128 bits in EVERY circuit
    (deposit, transfer, withdraw).

================================================================================
                    ON-CHAIN ENCRYPTION KEY (2026-09-25)
================================================================================
WHAT WAS WRONG
  register() bound a wallet address to its user commitment and nothing else.
  But a sender needs TWO things about a receiver:

      user_commitment       — to lock the note commitment to them
      encryption_public_key — to encrypt the note so only they can read it

  and the second cannot be recovered from the first (the commitment is a
  Poseidon hash). So the encryption key was written to Mongo at registration
  time and every send asked the BACKEND, not the chain:

      GET /api/register/:network/status/:address

  That put a server on the critical path of a privacy decision, and it has
  three ways to answer wrong:

    1. The backend is down / cold-starting  → the lookup throws.
    2. The backend's configured pool address is stale, or its RPC answers a
       rate-limited eth_call as a revert → "registered: false" for a wallet
       that IS registered.
    3. Mongo has no row (registered on another device, DB reset, a different
       backend) → "registered on-chain, but no encryption key on record".

  Cases 2 and 3 are what produced the reported bug: paste an address that is
  demonstrably registered, and the send modal says it is not. Worse, a
  "registered: false" is ACTED ON — the modal falls back to a public withdraw.
  Quietly sending in the clear is the one outcome a privacy wallet must never
  produce by accident.

THE FIX
  register() now takes the encryption public key too, and stores it on-chain:

      EVM     register(bytes32 userCommitment, bytes encryptionPublicKey)
              mapping(address => bytes) public encryptionKeys
              registrationOf(addr) -> (bytes32, bytes)
              isRegistered(addr)   -> bool
      Solana  register(user_commitment: [u8;32], encryption_public_key: [u8;32])
              Registration { wallet, user_commitment, encryption_public_key, bump }
      Aptos   register(user, pool_addr, user_commitment, encryption_public_key)
              #[view] registration_of(pool_addr, wallet) -> (bool, u256, vector<u8>)
      Sui     register(state, user_commitment, encryption_public_key, ctx)
              registration_of(state, wallet) -> (bool, u256, vector<u8>)

  Key format per chain (raw bytes on-chain, encoded in the wallet):
      EVM     65-byte uncompressed secp256k1 (0x04 ‖ X ‖ Y) -> 0x hex
      Solana  32-byte ed25519                                -> base58
      Sui     32-byte ed25519                                -> base64
      Aptos   32-byte ed25519                                -> 0x hex

  The combined readers NEVER abort on an unregistered address — they answer
  (false, 0, empty). A wallet has to be able to tell "not registered" from "the
  node did not answer", and an abort makes those two look identical.

  The wallet (extension + app) now resolves a recipient straight from the chain
  through its own RPC list, with the backend only relaying the signed register
  transaction. The /register/:net/status/:addr endpoint still exists and now
  also reads the key from the chain, but nothing in the send path needs it.

DATABASE
  The backend treats its Mongo DB as the source of truth — no indexer scans the
  chain (see poolIndexer.js / aptosIndexer.js / suiIndexer.js). State is keyed
  by NETWORK NAME, not pool address, so every network's documents had to be
  cleared: all six pools are empty on-chain and the DB must say the same, or
  every Merkle proof it builds is against a root that does not exist.

      node wallet/backend/reset_network_state.js --all

  NoidRegistration rows were dropped too. They described wallets registered
  against the old pools, which no longer exist; the encryption key now comes
  from the chain, so nothing depends on that collection any more.

BUILD PINS (Solana)

  build crates that require 1.85. Four crates are pinned back in Cargo.lock:

      indexmap              2.14.0 -> 2.7.1   (pulled hashbrown 0.17 / edition2024)
      hashbrown             0.17.1 -> 0.15.5  (follows indexmap)
      unicode-segmentation  1.13.3 -> 1.12.0  (requires rustc 1.85)

  Keep them pinned until the Solana toolchain's rustc moves past 1.85.
